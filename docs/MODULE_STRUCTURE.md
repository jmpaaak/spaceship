# 모듈 구조 — 상시 구조화 / 모듈화 / 캡슐화 (2026-09-08)

기능 개발·리팩토링·버그수정 **모두에서 항상** 구조화·모듈화·캡슐화를 적용한다.
목표는 **병렬 개발이 가능**하고 **유지보수가 쉬운** 코드다. 한 파일에 동작을 계속 붙이지 않는다.

이 문서는 LÖVE 스켈레톤에서 파생된 모든 프로젝트와 자율 루프 `loop/PROMPT.md`의 원본이다.
PROMPT에는 아래 **최우선** 단락만 두고 상세는 여기로 보낸다.

## 최우선 (사용자 2026-09-08)

INBOX 기능보다 **구조화 / 모듈화 / 캡슐화 리팩토링이 먼저**다.

1. 매 사이클, 손대려는 파일이 **800줄 또는 80KB**를 넘으면 그 사이클의 유일한 작업은 **모듈 분리**다. GREEN+커밋 전에 그 파일에 새 기능을 넣지 마라.
2. 새 기능은 **담당 모듈**에만 넣는다. 거대 엔트리(`play.lua` / `main.lua` / `self_test.lua`)에는 `require` + 한 줄 위임만.
3. **캡슐화:** 순수 규칙(`game/*.lua`, `love.*` 없음)과 씬 드로우/입력을 섞지 마라. 모듈은 작은 공개 API만 내보낸다.
4. 슬라이스 = **모듈 1개**. 예: `game/scenes/play_hud.lua`, `game/ui/slot.lua`, `story/foo.lua`.
5. INBOX 최상단이 기능이어도, 그 기능이 거대 파일에 붙어야 하면 **먼저 그 파일을 쪼갠다**. 이미 독립 모듈 경로가 적힌 항목만 기능 진행.

## 한도

- 한 Lua 파일이 **800줄 또는 80KB**를 넘으면 기능 추가가 아니라 모듈 분리 리팩토링이다.
- `play.lua` / `main.lua` / `self_test.lua`를 더 키우지 마라.
  `self_test`는 시나리오별 상위 함수 또는 `game/tests/<topic>.lua`.

## INBOX 최대 병렬 (사용자 2026-09-07)

처리 대기 목록을 **가능한 단위로 최대로** 워크트리 병렬화한다. 모듈 분해가 병렬도의 전제다.

1. 각 INBOX 항목에 **담당 파일/모듈**을 명시한다.
2. 터치 파일이 겹치지 않으면 각각 `git worktree add` + 전용 브랜치 + 레인 `PROMPT.md`.
3. 같은 거대 파일을 만지는 항목은 **그 파일을 모듈로 쪼개기 전까지 직렬**.
4. **예외 — 이미 독립인 항목은 즉시 WT:** JSON+전용 모듈, `tools/` 에디터, 에셋 스크립트, 순수 `game/*.lua`(씬 비의존).
5. 한 레인 = 한 모듈. 같은 파일을 두 레인이 동시에 만지면 금지.
6. 메인 워크트리의 dirty 거대 파일에는 강제 checkout/pull 금지. 슬라이스는 레인에서 푸시, 메인에서 merge.

## 새 기능 체크

1. 이 동작이 들어갈 **새 또는 기존 작은 모듈** 이름을 정한다.
2. 거대 씬에는 `require` + 한 줄 위임만.
3. 테스트는 그 모듈을 직접 require한다.
4. INBOX 한 줄에 담당 모듈 경로를 적는다 — 없으면 루프가 전부 엔트리 파일에 붙여 1레인이 된다.
